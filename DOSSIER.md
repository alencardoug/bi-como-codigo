## 7. Where I hesitated

Decisions that could have gone the other way, with the reason they went this one.

1. **Salt and iterations repeated in every slot**, rather than once per profile in a table at the
   head of the header. Chosen so that one envelope is self-describing (the complete vector
   opens with itself, the password and the expectations) and checked against the manifest so
   the copies cannot diverge silently. Cost: a few bytes and one more check.
2. **The browser relies on CI for duplicate-key refusal of the manifest** (§4), and does not
   interpret the control totals at all (§2.4). The manifest the browser reads is the one the
   trusted release path published; authenticity is the release path's and HTTPS's, not the
   envelope's (PLAN §3.6). If that division is wrong, the browser needs a strict JSON parser.
3. **Step 1 of the reader checks the SHA-256 from the manifest first.** In the browser this
   catches any byte changed in the envelope before the cryptography, so the deeper checks
   (steps 3–8) are defence in depth there; they matter as primary checks where the manifest's
   hash is itself suspect, and the negative cases update the hash on purpose to reach them.
4. **No header-length field**: the header is parsed sequentially and its end computed, rather
   than stated and cross-checked. One fewer redundant field to keep consistent.
5. **`report_id` charset `^[A-Z][A-Z0-9_]{0,15}$`, not exactly `P01`–`P16`**: tight enough to
   keep one encoding per identity, loose enough that a report outside the 16 (stage 2.12) does
   not need format version 2. The expected identity comes from the manifest anyway.
6. **Iteration bounds 600,000–2,000,000** with exact equality to the manifest: the floor is N67;
   the ceiling is a denial-of-service guard for a tampered manifest, about one second here.
7. **IV uniqueness checked across the whole package**, although GCM only requires it per key,
   and every DEK is fresh: it is cheap and catches a broken generator. The reuse check needs
   the raw DEKs, obtained by unwrapping with the public passwords; AES-KW being deterministic,
   comparing wrapped keys under one KEK would also work, but not across profiles.
8. **`not_entitled` is decided before deriving** (step 5), so a visitor who picks the wrong
   profile does not wait for 600,000 iterations; nothing secret is revealed, the mapping is
   public in the manifest.
9. **Two producer layers** — a pure `seal_report` with explicit keys for vectors and the
   injected-reuse test, and `encrypt_package` with no random-source parameter — instead of one
   function with an injectable generator, so that no caller can make production deterministic.

### 3. Findings and evidence

**ENV-1-01 — Make each negative fixture reach the check it claims to prove**

**High → blocking.** `docs/encryption_envelope.md:218`, `:292`, `:298`, `:302`, `:306`, `:310`.
Evidence is **static control-flow analysis**, not execution of an envelope reader.

Step 1 checks the entire file's size and hash before parsing. The rows for altered wrapped keys,
salts, iterations and slot sets do not update those expectations; the concluding rule updates them
only “where the row says so.” They therefore stop at step 1, rather than steps 4 or 7. The
dossier's §7.3 claims a broader update policy, but the normative specification does not supply it.
Even granting that intended policy, these other contradictions remain:

| Fixture | Why the stated step is unreachable |
|---|---|
| `report_swapped`, P01 rewritten as P13, expected step 8 | P01 has only the `diretoria` slot; P13 requires `diretoria` and `logistica`. After updating size/hash and the report id, step 4 still rejects. Updating only the hash can also leave a size mismatch at step 1. |
| `package_swapped`, expected steps 3 and 8 | An unchanged foreign file first fails the original manifest hash. After updating size/hash and rewriting its package id, its fresh per-package salts still fail step 4 against the current manifest. |
| `iterations_altered`, minus one, expected step 4 or 7 | The vectors use 600,000; 599,999 must fail the bound at step 2, even after refreshing the hash. |
| `malformed`, expected “1 or 2” | An implementation that omits the particular parser check can still pass every such test through the unchanged step-1 hash/size check. |

This either makes conforming readers fail the proposed suite or encourages weakening assertions
until an absent security/format check passes silently. **Correction:** separate transport-integrity
tests from parser, manifest-binding, unwrap and GCM tests. Explicitly refresh size, hash and the
corresponding content-hashed filename for deeper tests. Specify the selected profile/slot and make
all preceding checks valid. Isolate report/package AAD tests using compatible slot sets and salt
expectations; do not re-seal after the final AAD mutation. Use an in-range iteration change for
the equality/unwrap cases. Give manifest-validation failures their own expected stage.

**Acceptance:** each fixture has one reachable refusal stage in both readers; disabling its target
check makes that test fail. In particular, malformed-envelope tests reach step 2, independently
of separate step-1 integrity tests. This requires correcting the design now and execution when
the implementations exist.

**ENV-1-02 — Prove DEK freshness independently of IV freshness**

**High → blocking.** `docs/encryption_envelope.md:322`, `:326`; key lifetime at `:44` and `:243`.
The specification forbids both repeated DEKs and repeated IVs across envelopes, but both injected
fixtures repeat the IV. Removing the DEK check leaves both prescribed rejection results unchanged.
Repeated DEKs with distinct IVs also matter to the access model: a DEK obtained through P13's
Logística slot could decrypt a P01 encrypted with that same key, using P01's public IV/header.

**Executed counter-proof of the fixture logic**, using only pairs of throwaway byte labels, not an
implementation of the package gate:

```text
prescribed same DEK + same IV: IV-only rejects=True, DEK-only rejects=True
prescribed different DEKs + same IV: IV-only rejects=True, DEK-only rejects=False
missing same DEK + different IVs: IV-only rejects=False, DEK-only rejects=True
```

The explicit “no two envelopes share a DEK” requirement was considered; it states the intended
behavior but does not repair this counter-proof gap. **Correction:** add a same-DEK/different-IV
fixture, keeping the rest of the package valid, alongside the existing different-DEK/same-IV case
and a valid control. **Acceptance:** removing either guard independently makes its dedicated test
fail; the valid control is accepted. Carry this separation into the live-package comparison in
stage 2.2b.

**ENV-1-03 — Define identity validation as a complete byte match**

**Medium → adjustment.** `docs/encryption_envelope.md:80`, `:97`, `:164`, `:166`, `:203`.
The document specifies regexes but no matching operation. Python's usual anchored `re.match`
accepts a final LF before `$`; JavaScript's regex without multiline mode rejects it. LF is an
ASCII byte and `P01\n` still meets the declared length bound. Thus two plausible implementations
written from the document disagree on validation. This is a protocol ambiguity, not a claim of
unauthorized access with today's fixed identifiers.

**Executed** with system Python and Node v24.18.0:

```text
identity bytes=5030310a
Python re.match(^[A-Z][A-Z0-9_]{0,15}$)=True
Python re.fullmatch([A-Z][A-Z0-9_]{0,15})=False
Node RegExp.test(^[A-Z][A-Z0-9_]{0,15}$)=false
```

The lowercase profile pattern has the same issue. **Correction:** state that every identity byte
must be consumed and belong to the listed ASCII ranges, with no newline exception, trimming or
normalisation; require that rule in the declaration, manifest and header. **Acceptance:** both
implementations reject a final LF (and other outside-charset bytes) in either identity, including
lengths within bounds, through the intended validation check after addressing ENV-1-01.

**ENV-1-04 — Separate fixture identifiers from observable refusal codes**

**Medium → adjustment.** `docs/encryption_envelope.md:228`, `:234`, `:292`, `:295`.

**ENV-3-01 — Give the framing equality one predicate, or define a distinct availability check**

**Medium → adjustment.** `docs/encryption_envelope.md:348`, `:440`–`:457`; the normative length
equation is at `:84`–`:87` and `:168`. **Introduced in revision 3** by the two-predicate inventory;
revision 2 required exact framing but did not assign two separately reachable predicate ids.
This is a confirmed specification/test-contract defect, not an observed production-reader bug.

Let `L` be the file length, `H` the parsed header length and `c` the declared ciphertext length.
With the fixed 16-byte tag, the literal checks are equivalent:

```text
ciphertext_len_equal: c == L - H - 16
exact_end:            H + c + 16 == L
```

Section 6.5 assigns `header_ciphertext_len` to the first and `header_trailing_byte` to the second,
and requires the unmodified module to return each exact predicate id. With equality first, an
appended byte already fails `ciphertext_len_equal`; removing `exact_end` changes nothing. With
`exact_end` first, it instead masks the length-mismatch cases. This includes `ciphertext_len`
one less than the file holds, expressly retained in §6.3: it leaves an extra byte just as the
appended-byte case does. No ordering of these two literal equalities makes both dedicated
original refusals reachable.

**Disproof considered:** a parser could compare `c` with the length of a slice read for the
ciphertext, reserving a subsequent end check for surplus bytes. That is a workable *availability*
check, but the declared-one-less variant then reaches `exact_end`, not its assigned
`ciphertext_len_equal`. The specification must define that split and the variant mapping if this
is intended; the current equality language does not do so.

**Executed evidence:** boundary-only models in Python and an ES module, with real header bytes
from the round-2 throwaway fixture (27 ciphertext bytes), reproduce the literal-equality reading.
Both copy/rewrite/import procedures ran under `/tmp`. Representative literal Node output:

```text

mutant ciphertext_len_equal / declared_minus_one -> ["header_malformed","exact_end"]; killed=true
mutant exact_end / trailing_byte -> ["header_malformed","ciphertext_len_equal"]; killed=false
```

deltas. These are models of the specified conditions, with other header checks stipulated and
cryptography omitted, not independent implementations or production vectors.

**Correction and acceptance:** preferably use one exact-file-length predicate and assign appended
bytes, in-range ±1 declarations and post-header truncations to it. Alternatively define separate
insufficient-data and surplus-data conditions, remapping the minus-one variant explicitly. Keep
`ciphertext_len_range` independent. Every retained predicate must have an original case reaching
its exact code/id with preceding predicates passing, and that case must kill its single-condition
mutant in both languages. No weakening to code-only assertions is needed.

**ENV-4-01 — Define and enforce the same numeric manifest contract**

**Medium → adjustment. Introduced by this implementation.** Python's `_is_int` accepts only
non-boolean Python integers; JavaScript's `Number.isSafeInteger` accepts integral values after
`JSON.parse`, which erases decimal/exponent spelling. Changing only `manifest_version` from
`1` to `1.0`, or `iterations` from `600000` to `600000.0`, or a valid `size` to the same number
with `.0`, makes Python refuse `manifest_invalid/manifest_types` while JavaScript validates and
**opens the unchanged P01 envelope**. Executed in `probes.py`, `probes.mjs` and `extra.mjs`:

```text
version_1.0 Python -> manifest_invalid/manifest_types
iterations_600000.0 Python -> manifest_invalid/manifest_types
size_integral_float Python -> manifest_invalid/manifest_types
version_1.0 JavaScript full open -> accepted
iterations_600000.0 JavaScript full open -> accepted
size_integral_float JavaScript full open -> accepted
```

The reverse mismatch also exists: `size = 9007199254740992` passes Python's validator and fails
JavaScript's. Both reject `size = -0`. A fractional literal `1.00000000000000001` rounds to 1
in JavaScript and opens, while Python refuses its float. These latter probes establish additional
numeric edges; the oversized size cannot match a format-v1 envelope and is not an access bypass.

**Disproof considered:** the current producer emits integer tokens, and the trusted CI path rejects
these changed manifests. There is no demonstrated release-path bypass. Nevertheless, ordinary
JSON serialization can emit integral decimal/exponent tokens; the explicitly requested reader
agreement, with duplicate keys as its exception, is unmet independently of hostile inputs.

**Correction/validation:** specify numeric value/type/range semantics in §4 and implement them
consistently, including `size`'s upper range. Account explicitly for information lost by
`JSON.parse`; do not try to distinguish decimal token spelling after parsing. Add shared integral
float/exponent, boolean, fractional, negative-zero and safe-integer-boundary cases, asserting the
same validation result and refusal pair in both runtimes. Preserve the production manifest control.

**ENV-4-02 — Validate the producer's totals before encryption**

future CI validation independently required.
