## 5. Assumptions about the environment

What was assumed about a tool, database or service and **not** confirmed in this
delivery. It is the class of error that passes code review unseen.

- `workflow_run` always runs the workflow file of the default branch, with `GITHUB_REF` the
  default branch, regardless of the triggering PR (§4).
- A `pull_request` run from a fork gets no secrets and cannot request an OIDC token; the design
  does not rely on it (`permissions: {}`), but T2's fallback does if no fork is possible.
- Google's workload identity provider evaluates `attribute_condition` before any binding, and an
  environment job's OIDC `sub` / `environment` claim is what `attribute.environment` maps.
- `roles/firebasehosting.admin` is the narrowest predefined role that deploys to channels and
  clones to live; no predefined role separates them (§5).
- GitHub does not let a PR's author approve it, so the `production` environment's approval is the
  only approval the Owner can give (§7).
- The Firebase CLI on this machine is 15.28.2; CI will pin its own version.

## 7. Where I hesitated

Decisions that could have gone the other way, with the reason they went this one.

1. **Three workflows** — candidate, publish (`workflow_run`), promote (`push` to `main`) — rather
   than one publishing workflow with two triggers: promotion has a different trigger, a different
   environment and its own concurrency group, and keeping it apart keeps each `workflow_ref`
   binding simple. Cost: two `workflow_ref`s in the provider's condition.
2. **The approval is the `production` environment's**, not a PR review — the Owner cannot approve
   their own PR. Everything the approval binds (version ID, digest) is re-checked after it.
3. **"Superseded" is decided by the tip of `main`** (§4.4, condition 1) rather than by comparing
   release timestamps: only the latest merge may promote. Cost: if two PRs merge quickly, only the
   second is promoted; the first's content is in the second's tree anyway.
4. **Two service accounts with the same role**, separated by environment, not by permission —
   Hosting has no finer predefined role, as far as I know. The separation is weaker than it reads;
   §5 says so.
5. **The record of a preview is a check run**, not a PR comment or an artifact: written only with
   `checks: write`, which the candidate workflow lacks. If check-run attribution is not as
   assumed, the record moves to a GitHub deployment of the `preview` environment.
6. **A ruleset with the Owner's bypass** instead of PRs required for everything (§6), chosen under
   N68 so that the Owner keeps pushing documents directly; promotion needs a previewed PR anyway.
7. **The protected set is one file**, `release/protected.txt`, inside itself, so that a PR cannot
   shrink it and get a preview in the same PR.
8. **No `pull_request_target`, no reusable workflow**: both would complicate what the token and
   the binding identify (RV4-01).
