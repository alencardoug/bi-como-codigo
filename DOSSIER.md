## 7. Where I hesitated

Decisions that could have gone the other way, with the reason they went this one.

1. **One Python module for every step**, rather than shell in the workflows: each condition is
   testable without the network, and the workflows stay thin.
2. **`admit` finds the PR by `commits/{head}/pulls`** rather than by `workflow_run.pull_requests`,
   which GitHub leaves empty for forks and is not documented as authoritative.
3. **`decide` ends green with "nothing to promote"** for a direct push or a stale run, red for
   everything else; `check-tip` in `promote` ends red.
4. **The served-bytes check decodes only `gzip`** and refuses any other `Content-Encoding`.
5. **`verify` finds the package as the one `manifest.json`** in the artifact, and checks the data
   keys and their hex form by content in every file.
6. **The release record artifact is kept 30 days**, the channel's life.
7. **`release/firebase-tools/package-lock.json`** (290 KB) is committed so that the CLI is the same
   bytes at every run.

### 3. Findings and evidence

**IMPL-1-01 — Critical — candidate ZIP extraction crosses the trust boundary.**
`publish.yml:53–58` downloads a PR-produced archive into `candidate/` before running trusted
Python; `publish.yml:98–104` repeats extraction in the job with an approved OIDC identity.
The exact pinned download action's [distributed source](https://github.com/actions/download-artifact/blob/d3f86a106a0bac45b974a628896c90dbdf5c8093/dist/index.js#L2233)
pipes the response into `unzip-stream.Extract`. Its bundled parser strips leading traversal
components, but leaves internal ones; the extractor uses `path.join(destination, entry.path)`
without checking containment (bundle lines 110371 and 109870).

**Executed:** fetched that exact bundle, changed only its startup export to expose module
73555, and called its production `streamExtractExternal` against a loopback HTTP server.
A ZIP containing `padding/../../trusted.py` overwrote a sibling of the destination:

```text
streamExtractExternal sibling overwrite: PR-controlled replacement
```

The probe wrote only under `/tmp/bi-review-zip`. It did not invoke the action entrypoint, upload
an artifact or request credentials. The honest upload action normally produces safe names;
that does not authenticate an archive from a job executing arbitrary PR code. Unprotected
tests can alter the candidate job's uploader at runtime. This upload mechanism is also
documented in the original researchers' [artifact privilege-escalation analysis](https://github.com/google/security-research/security/advisories/GHSA-cj34-9v6h-grxm).
The finding rests on the executed pinned bundle, not an advisory's affected-version range.

**Consequence, inferred from the workflow:** candidate extraction can replace `release.py` or
other executable files in `verify`. That compromised job can produce another traversal archive
as `verified`, replacing code before `preview` runs it with `id-token: write`. Google's provider
then sees the legitimate publisher on main in preview; federation cannot distinguish the
replaced code. Its Hosting Admin identity can deploy, including to live (§5).

**Correction / validation:** establish archive containment before any extraction can write to
the workspace, actions or runner control files. Use an independently verified safe downloader
or download without extraction and reject unsafe entries before safely extracting. A later
`verify` call is insufficient. Replay internal/leading traversal, absolute paths and link entries
against the exact replacement implementation; assert sibling code and runner control files are
unchanged, while both normal artifact layouts still work. No remote exploit was attempted.

**IMPL-1-02 — High — admission accepts the API's truncated file list.**
`release.py:389` reads `commits/{sha}/pulls`, whose response is `pull-request-simple`, without
`changed_files`. The code defaults the absent count to zero at line 405. After 30 full pages,
page 31 can be empty at GitHub's 3,000-file cap; the loop ends and neither count comparison
refuses it. A protected change outside the returned prefix therefore gets a preview, violating
§4.1/N74. The rename check itself correctly inspects `previous_filename`.

**Executed / source:** a GET for the pinned download action's associated PR returned
`changed_files_present: False`; GitHub's [REST schema](https://github.com/github/rest-api-description/blob/main/descriptions/api.github.com/api.github.com.json)
confirms the response type. A fake API supplied 3,000 harmless file objects, then an empty page,
for a PR whose omitted file is protected:

```text
3001-file PR; protected file beyond API cap; associated-PR response omits changed_files: 7
rename on page 2: PR #7 touches the protected set (release/protected.txt): no preview, no live update
```

**Correction / validation:** obtain the authoritative PR detail/count, refuse the cap
conservatively, and compare actual file-object counts with the expected count; rename aliases
must not inflate that count. Test absent metadata, 3,000/3,001 files, truncation below the expected
count, a protected second-page file and a rename out of the protected set. This is a security
condition explicitly required at admission, even though today's fixture is small.

**IMPL-2-01 — High — normal artifact downloads fail at the storage redirect.**
`fetch_artifact` passes the GitHub token into `_http`, which uses `Request.add_header` for
Authorization. Python carries that header into redirected requests. GitHub's archive endpoint
returns a signed storage URL; the GitHub bearer is not an Azure access token. The new downloader
therefore reaches storage with incompatible authorization and refuses its 401 before extraction.
Both publishing download steps use this path. The shared helper also serves `_artifact_json`.
This is a functional blocker for the pipeline, not a demonstrated PR-controlled redirect or
credential theft.

**Executed:** a loopback API with page-2 artifact discovery and a cross-origin 302 established
that the exact code forwards the sentinel. Independently, a read-only GitHub GET for public ZIP
artifact `11467106428` in `actions/upload-artifact` supplied a real signed storage URL. A local
redirect to that URL then exercised the **unchanged `fetch_artifact` and `_http`**. Only the
artifact-list response was substituted; no real credential was sent by Python:

```text
fetch-artifact: API page 2 -> 302 -> different-origin ZIP -> safe_extract PASS
Authorization sentinel sent to API: 3 requests; forwarded to blob: 1 request
public artifact 11467106428 ZIP signature: PK; redirect host: productionresultssa6.blob.core.windows.net
exact fetch_artifact, sentinel bearer: artifact 11467106428 answered 401
exact fetch_artifact, no forwarded bearer: extracted 2 files
```

**Counter-evidence considered:** the unsigned-header control succeeds against the very same
signed URL, ruling out expiry, permissions or a corrupt ZIP as the cause. The earlier local
server accepted any Authorization header, so its green result alone missed the real service's
behaviour. The workflows' actual `GITHUB_TOKEN` was not exercised; the normal-run consequence
follows from the executed header forwarding and Azure's rejection of the unrelated bearer.
[Python documents header propagation](https://docs.python.org/3.13/library/urllib.request.html#urllib.request.Request.add_header),
[GitHub documents the archive redirect](https://docs.github.com/en/rest/actions/artifacts#download-an-artifact),
and [Azure requires its own Entra access tokens for bearer authorization](https://learn.microsoft.com/en-us/rest/api/storageservices/authorize-with-azure-active-directory).

**Correction / validation:** authenticate the GitHub API request while keeping Authorization
off the signed storage request, for example with an unredirected header or an explicitly handled
redirect. Retain safe extraction. Add a download-path test whose API requires the bearer and
whose different-origin storage rejects it; assert both normal artifact layouts extract, API
errors fail closed, and traversal still writes nothing. Confirm a real signed ZIP download
without forwarding a GitHub credential. Changing the extractor cannot correct this defect.

`_paged` ignores `total_count` and returns when page 11 is empty, before its 50-page guard:

```text
_paged server cap: total_count=1001, returned=1000, calls=11, no incomplete-inventory refusal
```

A record outside that prefix is missed. **Counter-evidence / severity:** page-2 discovery and
ambiguity rejection now work; a missing record refuses promotion. Material impact requires more
than 1,000 newer successful publisher runs while the desired preview is still usable (under
29 days), implausible for this single-owner fixture stage. This is an observation under N72,
not an unsafe promotion path. Document the bound, or partition searches by creation time / refuse
an incomplete `total_count`; validate with the 1,001-result fixture before relying on larger
inventories.
